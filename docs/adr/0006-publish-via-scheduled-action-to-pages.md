# 0006. Publish the catalog from a scheduled GitHub Action to GitHub Pages

- Status: Accepted (the adaptive rate-of-change guard and failure alerting are not built, see Consequences)
- Date: 2026-10-14 (decision in [#24](https://github.com/csmarshall/ofd-to-spoolman/issues/24); design revised 2026-10-15; first live deploy 2026-10-15)

## Context

The catalog was originally built by a cron job and served by a container on a home server ([#12](https://github.com/csmarshall/ofd-to-spoolman/issues/12), [#13](https://github.com/csmarshall/ofd-to-spoolman/issues/13), both closed as superseded). On 2026-10-14 the maintainer decided to build and publish it from a GitHub Action, served by GitHub Pages from this repo, and to make the repo public ([#24](https://github.com/csmarshall/ofd-to-spoolman/issues/24)). The repo is public now (verified with the GitHub API on 2026-10-23; it was created on 2026-10-14, and the date of the visibility change is not recorded in the issues I read; the maintainer's account is 2026-10-15). The pre-publication tasks were genericising host-specific files ([#7](https://github.com/csmarshall/ofd-to-spoolman/issues/7), [PR #31](https://github.com/csmarshall/ofd-to-spoolman/pull/31)) and a decision on git history; per the maintainer the history was kept and a secret scan found nothing; I could not verify that scan, and GitHub's own secret scanning and push protection show as disabled on the repository (GitHub API, 2026-10-23), so it is only the maintainer's word. Sizing: filaments.json is about 11.5 MB raw and about 0.9 MB gzipped, Pages serves gzip with `max-age=600` and ETag, and the projected load was about 28 MB per install per month against a 100 GB/month soft limit, roughly 3,500 installs (all projected; the 304-after-expiry path was not yet observed end to end, [#24](https://github.com/csmarshall/ofd-to-spoolman/issues/24) comment of 2026-10-15).

## Decision

- Trigger: [.github/workflows/catalog.yml](../../.github/workflows/catalog.yml) runs on a schedule (`30 5 * * *` UTC, nightly) plus `workflow_dispatch`. The header comment records that OFD has released its dataset between about 01:00 and 03:03 UTC, so 05:30 leaves roughly 2.5 hours of margin. The issue originally proposed hourly; nightly is what shipped. Checked on 2026-10-23 against OFD's run history: its `build-dataset` workflow ran between 00:00 and 01:05 UTC on 2026-10-16 to 2026-10-23 and published its release at about 00:12 to 01:06 UTC (later than that on none of those days), so the margin is currently closer to 4.5 hours than 2.5; OFD's own `update_profiles` job commits slicer mappings to `main` at about 03:00 UTC, after the build, so those edits reach the dataset (and this catalog) a day later. Our run starts at about 05:42 UTC because GitHub delays scheduled runs. How the schedule should follow OFD's release more closely is an open question, see [ADR 0007](0007-upstream-spoolman-exporter-to-ofd.md).
- Build and guards: it runs `ofd2spoolman.py` against the committed `catalog/` as baseline. Any guard failure (fetch, duplicate ids, whole-catalog or per-source shrink, SpoolmanDB superset, corrupt baseline; exits 2 to 7) fails the run and skips the deploy, so the last good catalog stays live. Exit 10 (published with warnings, such as OFD looking stalled) commits and deploys with a warning annotation ([PR #16](https://github.com/csmarshall/ofd-to-spoolman/pull/16)).
- Provenance and freshness: `catalog/state.json` records the OFD dataset version and commit behind its `dataset-v<version>` tag, the SpoolmanDB deployment commit, the converter commit, the Last-Modified and sha256 of each fetched input, and the count and sha256 of each output. A freshness check warns when exactly one of Last-Modified and content hash moved between runs; it never blocks ([PR #16](https://github.com/csmarshall/ofd-to-spoolman/pull/16)). The design discussion proposed a `manifest.json`; what shipped is `state.json` doing that job.
- History: the Action commits `catalog/` (one record per line, sorted by id) to `main` only when content or the OFD version changed, with a subject like `catalog: OFD 2026.10.13 (db31453) + SpoolmanDB 8f1a99f + ofd2spoolman 3a3f2a2`, so `git log -- catalog/` is the index. The decision of 2026-10-15 chose a folder on `main` over the earlier orphan-branch proposal. CI ignores `catalog/**`, and the commit step fails if anything but a visible file in `catalog/` is staged. Pages is deployed with `actions/deploy-pages` from that folder, not a gh-pages branch. In a local aggressive-gc experiment git delta compression projected growth of a few MB a year; GitHub's own repacking may differ ([#24](https://github.com/csmarshall/ofd-to-spoolman/issues/24)).
- Rollback and pin: `workflow_dispatch` with `deploy_ref=<commit>` deploys `catalog/` as committed at that commit (must be on `main`); a repo variable `CATALOG_PIN` makes the nightly keep deploying that commit until cleared. This was exercised by hand on 2026-10-15 ([PR #33](https://github.com/csmarshall/ofd-to-spoolman/pull/33), [#24](https://github.com/csmarshall/ofd-to-spoolman/issues/24) comment). The pin is set manually because `GITHUB_TOKEN` cannot write repository variables.
- Trigger alternatives (open consideration, not a decision): the maintainer asked whether a release-triggered action would be better. A GitHub Actions `release` event fires only in the repo that owns the release, so this repo cannot trigger on OFD's `dataset-vYYYY.MM.DD` releases directly. The options are a more frequent cheap poll that builds only when the OFD dataset version or SpoolmanDB changed (the freshness checks already compare Last-Modified and content hash), or OFD sending a `repository_dispatch` to us, which would need a change and a token in OFD's workflow and is not something to ask lightly. A release-only trigger would also miss SpoolmanDB updates, which change independently of OFD. Tightening the schedule (for example hourly from about 01:00 to 06:00 UTC, building only on change) is open and undecided. In the upstream-exporter design ([ADR 0007](0007-upstream-spoolman-exporter-to-ofd.md)) the exporter runs inside OFD's own build, so no extra trigger is needed there.

## Consequences

Good: no server to run, visible failures (a failed run emails the maintainer), every published state is a commit that can be diffed or rolled back, and the first Pages deploys matched `state.json` hashes on 2026-10-15. The Pages catalog has run daily since 2026-10-16 with six consecutive successes as of 2026-10-21, and its filaments.json equalled the home-server build entry for entry (29,554 entries; [#5](https://github.com/csmarshall/ofd-to-spoolman/issues/5), comment of 2026-10-21). That is evidence of agreement between two builds of the same converter, not of data correctness.

Bad / limits: availability is best-effort with no SLA. Not built: an adaptive rate-of-change guard that would hold abnormal churn ([#29](https://github.com/csmarshall/ofd-to-spoolman/issues/29), open; its quantile and window choices are policy, not measurements) and alerting through a tracking issue ([#34](https://github.com/csmarshall/ofd-to-spoolman/issues/34), open); only the absolute guards exist, and the issue's measurement of 120 release pairs shows legitimate swings of over a thousand entries, so a fixed threshold would not do. Publish durability (fsync, empty-catalog refusal) is still open as [#22](https://github.com/csmarshall/ofd-to-spoolman/issues/22). While pinned, the bad commit remains the guard baseline, so a catalog that was inflated needs a `git revert` before nightly builds stop tripping the shrink guards (documented in the README). Scheduled workflows on public repos are disabled after 60 days without activity; the catalog commits count as activity, but only when data changes. Freshness checks cannot tell stale from correct, and GitHub Pages' Last-Modified reflects the deploy, not the data.

## Alternatives considered

- Keep the self-hosted container and cron. Superseded by this decision ([#12](https://github.com/csmarshall/ofd-to-spoolman/issues/12)).
- A dedicated orphan `catalog` branch with a separate manifest (proposed 2026-10-15, replaced the same day by a folder on `main` so there is no second ledger to drift from git).
- Commit the catalog to a gh-pages branch: rejected, it adds an 11 MB file to history per change and the artifact deploy avoids it.
- Release-triggered builds: see the open consideration above.
